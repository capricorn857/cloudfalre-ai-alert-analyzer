今天分享 Cloudflare AI 告警分析系统。我们用一条 WAF 告警串起三个问题：原始告警缺少哪些上下文，如何在 Workers 上完成可靠的异步分析，以及怎样让 AI 的判断受到证据约束。听完后，大家应该能解释这条链路，也能判断哪些输出值得参考、哪些仍需人工核验。

# 02_problem

【计时】本页 2:00；累计 2:30。

假设我们收到左侧这条告警：example.test 的 WAF 安全事件突然增加，告警参考事件数是 1,000，动作字段是 allow。这里的域名、数字和后续案例都经过虚构，不是生产事件。

现在可以知道发生了异常，但还不能直接采取处置。至少有三个问题没有答案：来源是什么，目标是什么，Cloudflare 已经做了什么。来源可能集中于少数 IP，也可能分散；目标可能集中在一个业务 Host，也可能只是多个站点的背景噪声。这些情况的核验路径不同。

请大家想一下，自己收到告警后的第一个动作是什么。通常是打开 Dashboard，选择时间窗口，再逐个查看 IP、路径和动作分布。停顿约十秒，请一位同事回答，随后回到主线。本项目希望自动整理这部分上下文，让通知成为排查入口。

这里特别强调两点。第一，Security Events 增加不等于攻击意图已被证实。第二，Payload 的事件数只是告警参考值，不能直接拿它给后面所有统计做分母。后续比例来自固定窗口下的 GraphQL 聚合，二者可能因时间和采样口径不同而不相等。幻灯片为了便于理解用了相同数字，但代码没有强制它们一致。

【过渡】围绕这个问题，我们刻意缩小了系统边界。

# 03_scope

【计时】本页 1:00；累计 3:30。

边界可以记住三个词：只读、一次快照、辅助研判。只读意味着系统读取 Cloudflare 数据、整理判断和建议，但不自动封禁 IP 或修改 WAF。一次快照意味着针对当前告警固定一个窗口，不持续追踪，不等数据收敛，也不产生初报和终报两套流程。辅助研判意味着最终决定仍由运维和安全人员完成。

这些约束直接影响架构。我们不需要做后台、历史检索或持久化事件生命周期；也不把模型接入配置变更权限。减少能力范围之后，更容易把数据口径、故障行为和输出边界讲清楚。这是一个用于告警分析的工具，不是完整 SOC 平台。

# 04_outcome

【计时】本页 1:30；累计 5:00。

先看结果，再讲实现。左边是原始告警，右边是虚构的分析通知摘要。右边新增了业务 Host、该 Host 的快照事件总量、目标路径的数量与比例，以及 allow 和 block 的处理分布。比如 api.example.test 有 600 个事件，其中 /api/login 有 300 个，占这个 Host 的 50%。注意分母是 600，而不是 Zone 的 1,000。

这些信息不是让我们马上封禁，而是让我们知道应该核验哪里。例如，优先看这个 Host 的登录路径，确认主要来源是否属于正常业务，再结合应用日志看是否真的存在异常。allow 80% 只能表示快照安全事件的动作分布，不能解释为 80% 的已确认攻击穿透了防护。

真实通知还要保留固定窗口、覆盖信息、incident_id 和 correlation_id。页面为了投影可读性只放摘要，并非机器人真实截图。当前实现也不会为了页面好看而展示一段未经校验的模型原文。

# 05_architecture

【计时】本页 2:00；累计 7:00。

从左到右看，一条 WAF 告警通过 Webhook 进入 Worker 的 fetch Handler。这里完成路由与 Zod 校验，记录接收时间，固定分析窗口，最后写入 Queue。只有入队成功才返回 202；如果入队失败，不能告诉调用方已经接收成功。

入口不调用 GraphQL、LLM 或企业微信。因此响应无需等待完整分析，也避免把复杂外部调用绑定到 Webhook 的请求生命周期。Queue 按设定延迟投递。消费者实际开始执行时，校验并复用消息中的窗口，再进入 WAF Analyzer。

消费者内部先查询 Zone 总量和 Top Host，然后在同一窗口里对选中的 Host 分别采集聚合和样本，做确定性统计与规则分析。之后生成证据目录，交给模型；模型结果必须经过程序校验，再由 Formatter 生成企业微信文本。如果 AI 不可用，规则分析继续走到通知。

这里没有拆成多个微服务。同一个 Worker 提供 fetch 和 queue 两个 Handler，但代码职责分开：入口只做接入，Client 只负责外部通信，统计和规则尽量是纯函数，Formatter 管展示。index.ts 只组合依赖和注册 Handler。

【指图】先指上方五个节点，再指右下 Consumer 内部步骤，避免逐个模块名称展开。
【过渡】这也解释了为什么选择当前技术栈。
【依据】src/index.ts；src/api/cloudflare-alert.ts；src/pipeline；README.md。

# 06_stack

【计时】本页 1:30；累计 8:30。

技术选型围绕工作负载展开。我们的主要工作是 JSON 校验、外部 API 调用和有限的数据处理，Workers 原生 Handler 与 Fetch API 已经足够，不需要再引入 HTTP 框架或维护服务器进程。

Queues 承担异步任务和延迟投递。它让分析与 HTTP 生命周期解耦，但代价是我们必须接受至少一次投递，不能承诺永远只有一条通知。MVP 没有引入幂等存储，重复通知通过完整的事件标识辅助识别。

TypeScript 和 Zod 分别覆盖编译期与运行时。外部输入在进入业务前需要校验；模型输出同样属于不可信边界。Vitest 配合 Workers 插件测试真实运行时和 bindings，Wrangler 管理本地开发、类型生成和部署。

这种轻量方案的边界也很清楚：没有数据库，不提供历史检索，不自动追踪事件。如果未来需要持久化幂等或事件生命周期，就应重新评估架构和变更范围，而不是把这些能力偷偷塞进现有链路。

【过渡】轻量不等于随意，尤其是时间口径必须固定。
【依据】技术栈文档；README.md；package.json；vitest.config.ts。

# 07_window

【计时】本页 2:00；累计 10:30。

这一页是可靠性设计的关键。假设告警时间为 09:18:46 UTC，Webhook 在 09:19:00 完成校验、准备入队。默认向前取 30 分钟，所以开始是 08:48:46；默认缓冲 60 秒，所以截止是 09:20:00。

时间轴不是按真实比例绘制的，因为三十分钟与几十秒放在同一比例下不容易投影阅读。我们关心的是四个时间点的关系。结束时间在入队之前就已经固定，保存在 Queue Message 中。Queue 用延迟投递来缓冲上游聚合延迟，Worker 内没有主动 sleep。

再想一个情况：消费者因为调度延迟，09:22 才真正开始处理。是否把窗口扩到 09:22？答案是不扩。否则同一条告警的统计会因为排队时间变化而变化，技术重试也会变成重新分析。实际处理时间只用于日志和耗时观测。

空数据和低事件量也不触发第二轮采集。允许针对技术故障做有限重试，但所有请求复用原窗口。同一轮采集可以有多次 GraphQL HTTP 请求，并不意味着整个分析只有一次 HTTP 调用。

【互动停顿】问“如果重试发生在五分钟后，截止是否改变”，停顿数秒后指向右下答案。
【过渡】除了时间，另一个容易混淆的口径是 Host。
【依据】src/pipeline/window.ts；src/domain/queue-message.ts；固定窗口需求与 Host OpenSpec。

# 08_hosts

【计时】本页 2:00；累计 12:30。

这里沿用同一个虚构例子。Zone 一共有 1,000 个事件，api.example.test 有 600 个，www.example.test 有 300 个。剩下 100 个位于其他 Host，示例中不含 /api/login。

两个 Host 都有 /api/login，但含义不一样。在 api Host 上，这条路径有 300 个事件，占 600 的 50%；在 www Host 上，30 个事件只占 300 的 10%。如果按 Zone 合并，就只看见 330 除以 1,000，得到 33%。这个数字本身没有算错，但会掩盖具体业务 Host 的差异。

因此当前实现先做 Zone 发现，再对选中 Host 精确过滤、独立采集、独立统计和规则分析。默认选 Top 3，参数支持 1 到 5；后面的教学案例为了简洁显式使用 2。选择有限 Host 就意味着覆盖有限，不能暗示完整分析了所有站点。

还有一个分母要分清：UA 集中度来自样本，只能用该 Host 非空 UA 样本数作分母，不能冒充总体比例。采集失败也不能用零填充；零表示观测到没有事件，而失败表示不知道。发现与聚合口径不一致时，覆盖比例应显示未知。

【过渡】统计由程序明确之后，AI 才有一个可约束的输入。
【依据】src/analysis/host-analysis.ts；src/analysis/statistics.ts；Host OpenSpec；README.md。

# 09_responsibilities

【计时】本页 2:00；累计 14:30。

左边是程序负责的部分。事件总量、比例、速率、规则关注等级都由确定性逻辑计算。证据目录也是程序从已经校验的数据派生的。模型不能再去 Cloudflare 查询，也不能重算这些比例。

右边是模型负责的部分：在有限的结论和建议类型中提出候选结果，并为每项绑定证据。当前版本已经收紧了最初自由文本报告的设计，模型不能任意生成一段安全分析直接发送给用户。

Unknown 是一个正常且重要的输出。当前支持策略只开放满足条件的疑似 Bot 假设，其他具体攻击类型在证据不足时必须 Unknown。页面没有宣传可以可靠识别暴力破解、撞库或漏洞利用，因为这些结论需要更丰富的证据。CRITICAL 也没有已开放的支持规则。

再补充两个容易误读的概念。规则关注等级不等于已经证实的危害程度；当前比例阈值也不能替代业务影响评估。模型给出的置信度是受约束的自评，不是校准过的攻击概率。我们更在意输出能否被核验，而不是听起来是否果断。

【讲述提示】在“Unknown 是正常结果”处稍作停顿，让听众理解收紧表达能力的价值。
【过渡】仅要求模型引用证据够不够？还不够。

# 10_evidence

【计时】本页 2:30；累计 17:00。

这里有四个环节。首先是证据目录，每一项带有来源、Host 归属和相应口径。然后是结构校验，确认返回的是符合 Schema 的 JSON。第三步最重要：支持校验。不只看引用 ID 是否存在，还要看类型是否适配、有没有缺少必要证据、是否跨 Host、是否满足当前策略的阈值与样本条件。最后，Formatter 从经过验证的目录取值，按程序模板渲染。

看下面这个反例。某个 Host 的 Top IP 占 60%，/api/login 占 50%。这两个事实都可以成立，但它们是两份独立排名。我们不知道该 IP 的请求究竟有多少落在 /api/login，更没有登录失败、账号尝试等证据，所以不能推断这个 IP 正在对登录接口实施暴力破解。

即使模型把两个真实引用都列出来，联合关系也没有因此成立。当前系统不做 Host+IP+Path 交叉归因，不应通过自然语言拼出这种关系。这正是“引用存在”和“引用能支持声明”之间的区别。

可以给听众十秒，思考如果要支持这个结论，还缺少什么。可接受的方向包括联合维度请求证据、应用认证结果、账号维度与业务上下文。但这些是讨论方向，不代表项目已经具备，也不能自动加入现有生产查询。

最后提醒，这种校验验证的是预先规定的支持策略，不能证明上游数据完全准确，更不能证明攻击意图或实际损失。它降低了无依据输出的空间，而不是把模型变成绝对可信的裁判。

【过渡】校验拒绝输出后，告警会不会消失？
【依据】src/analysis/host-evidence.ts；src/analysis/evidence.ts；结构化证据与 Host OpenSpec。

# 11_failures

【计时】本页 2:00；累计 19:00。

答案是不会因为 AI 不可用就丢弃整条告警。我们按失败发生的位置处理。某个 Host 数据采集失败时，临时错误有限重试，最后明确标记失败和未知，同时保留其他 Host 的结果。若整个 Cloudflare 数据采集失败，就发送基础异常通知，而不是让模型补造统计。

如果只是一个 Host 的 AI 输出语义无效，仅该 Host 回退到规则分析；如果整个响应根结构无效，就让全部 AI 降级。两种情况都保留已经获得的统计和规则，不重新查询、不移动窗口，也不因为模型输出错误重放 Queue。

企业微信阶段只重试发送已经生成的文本，不再做一次 GraphQL 和 AI 分析。最终发送失败会记录并确认消息，这是当前设计的有限重试边界，意味着不能保证每条通知最终送达，需要通过日志和运维观测发现问题。发送成功之后，后续观测异常也不能再抛出导致整条消息重放。

与此同时，Queue 本身是至少一次投递。在极端情况下仍可能重复消费或重复通知，所以通知中必须保留完整 incident_id 和 correlation_id。我们没有持久化幂等存储，不能声称恰好一次。

# 12_case

【计时】本页 3:00；累计 22:00。

这一页把前面的虚构场景完整串起来。告警时间是 09:18:46 UTC，接收时间是 09:19:00，所以固定窗口是 08:48:46 到 09:20:00。本例将 hostLimit 设为 2，选择 api 和 www 两个 Host；这只是演示配置，默认值仍然是 3。

GraphQL 发现 Zone 总量为 1,000。api 有 600 个事件，其中 /api/login 为 300，allow 为 480，block 为 120。www 有 300 个事件，其中 /api/login 为 30，allow 为 30，block 为 270。两边 challenge 都为零。本例假定聚合完整、发现与采集计数一致。因而覆盖估计为 900 除以 1,000，即 90%。如果这些前提不成立，就不能机械地展示 90%。

程序据此计算独立比例和规则 Finding，再生成证据目录。假设模型结构和支持校验通过，但不足以支持具体攻击类型，则返回 Unknown。当前 Formatter 隐藏 Unknown 的占位文案，仍然保留防护分布、来源路径、必要限定语和人工核验建议。Unknown 与 AI 调用失败不是同一回事：前者是合法结果，后者要明确显示 AI 降级。

这时值班人员可以按通知里的窗口进入 Dashboard，先核验 api Host 的路径集中度，再结合业务日志判断是否异常。不能因为 allow 80% 就断定 80% 的攻击穿透，也不能因为 www 的 block 90% 就声称业务绝对安全。

# 13_verification

【计时】本页 1:30；累计 23:30。

测试不只验证一条正常路径。第一层是数据契约与纯函数：Schema、窗口、Host 分母、证据支持、样本口径。第二层是 Workers 运行时：路由、Queue binding、Fetch Mock 和外部失败组合。不能只在普通 Node 环境跑过就假定 bindings 正常。

第三层是安全与通知边界。需要检查日志不泄露 Token、Prompt 或模型原文；通知在 2000 UTF-8 字节预算下仍然保留必要状态、窗口和完整 ID；压缩时整项省略，而不是截掉半条结论。第四层是有授权后的真实接口核验，在 Dashboard 选择同一窗口、同一 Host，对照聚合与采样差异。

OpenSpec 在这个过程中明确需求和契约变化；先写失败测试，再做实现，最后做类型、Lint、测试和影响检查。Mock 能证明程序对给定响应的处理行为，但不能替代真实模型兼容性与部署验收。

【备选问答】
1. 为什么不自动封禁？本项目定位为只读辅助研判，当前证据不能充分证明意图和业务影响；自动变更需要独立设计与授权。
2. 为什么经常是 Unknown？当前支持范围有意收紧，Unknown 比无依据的具体攻击标签更准确。不能以降低 Unknown 为目标放宽支持条件。
3. 为什么没有数据库？一次快照通知不需要持久化生命周期；若将来需要历史检索或幂等存储，应作为新的架构变更评估。
4. block 100% 是否表示完全安全？只说明本 Host 本次快照中观测到的事件都标记为 block，不证明全部攻击被阻止，也不代表业务没有其他风险。
5. 如何保证通知只发一次？当前不能保证。Queue 至少一次投递，完整 ID 用于追踪；持久化幂等不在当前范围。
